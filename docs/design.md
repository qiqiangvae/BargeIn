## 1. 背景与定位

Barge In 是 macOS 上的身体节律提醒工具：常驻菜单栏，在需要的时候用**打断式的提醒呈现**把用户从工作里拽出来。

竞品调研的关键事实决定了产品形态：

1. 提醒的**硬阻断手段早都存在**（BreakTime `enforce`、MacBreakZ 整屏锁定、Time Out 延迟解除、Stretchly Strict Mode），但**全是藏在设置里的可选项**，没有产品把它当成可安装、可出售的体验。
2. 整个品类把"提醒长什么样"当成写死的功能，**没有任何竞品把提醒呈现层做成可更换、可配置的内容**。
3. 该品类头部产品把"不打扰"当政治正确（Smart Pause、自动避让），"能打断心流"是逆风位，也是未被占据的位置。
4. 赛道收入天花板有数：头部 LookAway 开发者自述净收入约 $5k/月。这是"Mac 单人独立开发 + 单一小工具"的量级。
5. 喝水与休息分属两个品类，**无人合体**。
6. 品类里日历只被用来**避让**（会议期间不提醒），**没有一家用日历决定"什么时候该打断你"**。日程场景就是把这个方向反过来用。

产品定位：**一个身体节律引擎；它的提醒呈现由内置预设驱动，每个预设可以在每个场景下被实例化、改名、改文案、复制出更多张，呈现资源本身将来可以成为商品。场景有三个：喝水、活动、日程。**

日程场景是整个产品唯一联网的能力：只读订阅用户自己填写的日历地址，或用户自己在日历服务里生成的 CalDAV 凭据（[ADR-0001](adr/0001-network-for-calendar-subscriptions.md)）。没有账号体系、没有内置服务对接、没有写回、没有遥测。

## 2. 目标与非目标

**目标（v3）**

- 三个场景：喝水（累计量）、活动（纯定时）、日程（订阅日历的事件前置提醒）。每个场景有自己的启用开关、触发来源、预设实例与账本。
- 日程场景的触发来源是外部日历：订阅 → 拉取 → 解析 → 事件按"开始时刻 − 前置"触发。前置全局一个值，默认 5 分钟。
- 日程场景**不受工作时段与休息日约束**（事件自带时间），仍受免打扰。
- 提醒队列的去重键从 `SceneID` 改为 `(SceneID, 事件标识)`：喝水与活动每场景最多一条，日程按事件各一条。
- 日程的只读取数支持两条传输：一条日历地址（ICS，可选 Basic Auth），或一套 CalDAV 凭据（钉钉、企业微信、飞书、iCloud 私有、Nextcloud 等）。密码存 Keychain，每 30 分钟与唤醒时刷新，失败保留缓存并标注过期，不静默丢提醒。
- 设置窗口分四个 tab（喝水 / 活动 / 日程 / 通用）；日程 tab 有「订阅」与「前置」，没有「节奏」。
- 日程场景出厂**停用**；添加订阅并成功拉取后提示开启。
- `--selftest` 覆盖日历解析、重复事件展开与改期覆盖、豁免规则、按事件去重的队列、失败降级与已提醒不重弹。

**非目标（v3 明确不做）**

- CalDAV 的写操作（`PUT` / `DELETE` / `MKCALENDAR`）、`sync-token` 增量、ETag 条件请求、OAuth 2.0、RFC 6764 完整发现链、共享日历的权限管理。
- 内置任何服务对接（Google 账号登录、iCloud 登录、Exchange/Graph）。
- 事件编辑、创建、删除；`VALARM` 读取；会议链接、参会人、日历颜色。
- RRULE 长尾：`BYSETPOS` / `BYYEARDAY` / `BYWEEKNO` / `BYMONTHDAY` 组合。
- 全天事件的定时提醒；事件结束提醒；跨天事件的结束边界。
- 合并呈现、优先级策略、久坐检测、统计图表、云同步、账号、iOS 端、通知中心、AppleScript/Shortcuts。
- 场景插件化：不做注册表、清单文件、目录扫描、可安装场景。

## 3. 整体设计

### 3.1 运行形态

| 部件 | 实现 |
|---|---|
| 进程形态 | `LSUIElement = true`，无 Dock 图标 |
| 常驻入口 | `NSStatusItem` + `NSPopover` |
| 设置窗口 | 独立 `NSWindow`（SwiftUI 内容），仅用户主动打开；内含四个 tab，预设网格直接列出该场景的全部卡片 |
| 提醒层 | 每个连接的屏幕一个无边框 `NSPanel`，覆盖全部屏幕；同一时刻只有一条提醒 |
| 网络 | **默认零网络**。只有日程场景启用且配置了订阅时，才向用户填写的地址发只读 GET |
| 本地数据 | `UserDefaults` 存状态；`Application Support/BargeIn/` 存订阅缓存；Keychain 存密码 |

### 3.2 模块划分（SwiftPM 多 target）

```
BargeInCore/          场景无关：SceneID、SceneDescriptor、SceneConfig、SceneTrigger、
                      TimeOfDay、Schedule、SceneRuntime、FirePlan、Preset、Presentation、
                      CopyText、Ledger、ReminderKey
SceneWater/           喝水状态（WaterState）+ 场景描述（WaterScene）
SceneActivity/        活动状态（ActivityState）+ 场景描述（ActivityScene）
SceneSchedule/        日程：订阅模型、ICS 解析、RRULE 展开、事件（EventOccurrence）、
                      场景状态（ScheduleState）+ 场景描述（ScheduleScene）
BargeIn/              AppState、StateStore、ReminderEngine、订阅拉取与缓存、
                      Keychain、popover、设置、提醒层、品牌、DevSnapshot、SelfTest
```

- `BargeInCore` 只依赖 Foundation，不引入 SwiftUI/AppKit。
- 场景模块只依赖 `BargeInCore`，各自持有自己的 Codable 状态、默认文案、变量与完成动作标签。
- `SceneSchedule` 依赖 Foundation 与 `URLSession`，负责"地址或 CalDAV 凭据 → 事件列表"的纯数据链路（含 CalDAV 的 `PROPFIND` / `REPORT` 请求构造与 XML 解析）；**弹窗、Keychain、缓存目录、定时器都在 App 层**，场景模块不认识 UI 与钥匙串。
- `BargeIn`（可执行 target）依赖四者，显式组装三个场景，不做注册表/发现。

**装配点**：`SceneRegistry` 是一份写明三个内置场景的静态列表，靠 `SceneID` 闭合枚举查表；加第四个场景 = 加一个 case + 一个场景模块 + 一张默认配置，不是插件。

### 3.3 数据流

```
用户改动/完成 ──► AppState ──► UserDefaults
                    │
Scheduler ──► 到点 ──► ReminderQueue(ReminderKey) ──► 当前场景的预设实例
                                              ├─► 档位表 + 场景账本 ──► 呈现参数
                                              ├─► 文案槽 + 实例覆盖 + 场景变量 ──► ReminderPanel
                                              └─► SoundPlayer
                    │
                    └──── 完成/推迟/中断（只作用于当前场景） ◄──── 场景动作

订阅（日程）：
地址 ──► GET ─────────────────┐
                             ├──► VCALENDAR 文本 ──► ICS 解析 ──► 事件窗口 ──► 本地缓存
CalDAV 凭据 ──► REPORT ──────┘                                        └──► 重算下一次触发
```

单一状态源 `AppState`，所有 UI 与调度都读它；任何写操作都落盘并重算下一次触发时间。预设、档位表、场景描述是引擎内的常量，不参与持久化。网络只在"刷新订阅"这一条路径上发生，失败不改变已有缓存。

### 3.4 代码分包边界

| 位置 | 放什么 | 不放什么 |
|---|---|---|
| `BargeInCore` | 调度、账本、预设、文案解析、场景 ID/描述/配置类型、队列键 | 具体场景的业务字段、ICS 解析、SwiftUI、AppKit |
| `SceneWater` | 配额状态、喝水默认文案/变量/完成标签 | 调度器、账本实现、UI |
| `SceneActivity` | 今日次数、活动默认文案/变量/完成标签 | 调度器、账本实现、UI |
| `SceneSchedule` | 订阅模型、ICS 解析与 RRULE 展开、CalDAV 请求构造与 XML 解析、事件时间窗口、日程默认文案/变量/完成标签 | UI、Keychain、缓存目录 |
| `BargeIn` | `AppState` 聚合、`StateStore`、`ReminderEngine`、订阅调度与缓存、Keychain、全部 UI、`SceneRegistry` | 场景私有的业务规则、ICS 语法与 DAV 协议细节 |

## 4. 核心模型

### 4.1 场景

```swift
enum SceneID: String, Codable, CaseIterable { case water, activity, schedule }

struct SceneDescriptor {
    let id: SceneID
    let title: String                 // 喝水 / 活动 / 日程
    let summary: String               // 设置页的一句说明
    let defaultTrigger: SceneTrigger
    let defaultCopy: [CopySlot: String]
    let variableNames: [String]
    let completionLabel: String       // 喝了 / 活动了 / 知道了
    let completionSymbol: String      // SF Symbols
}

struct SceneConfig: Codable, Equatable {
    var isEnabled: Bool
    var trigger: SceneTrigger
    var instances: [PresetInstance]
    var activeInstanceID: UUID
    var skipsToday: Int
}
```

| 归属 | 内容 |
|---|---|
| 按场景 | 启用开关、触发来源、预设实例与激活项、账本、场景私有业务数据（喝水配额 / 活动次数 / 订阅与事件缓存） |
| 全局 | 工作时段、休息日、免打扰 1 小时、跨日边界、`hasOnboarded` |

喝水与活动**出厂启用**，日程**出厂停用**（没有订阅就没有数据）。停用只停调度，不清账本与进度；`免打扰 1 小时`是临时全局静音，两者独立。

### 4.2 喝水的配额模型

| 概念 | 规则 |
|---|---|
| 日目标 | 默认 2000 ml，用户可改 |
| 单杯量 | 默认 250 ml，用户可改 |
| 进度 | `consumedML` 累加；进度模板渲染 "750 / 2000 ml" |
| 完成动作 | 一键"喝了" = +单杯量；popover 里点水位环也记一杯，杯量只认设置里的单杯量 |
| 达标 | `consumedML >= targetML` 时当天不再提醒，至次日重置 |
| 跨日重置 | 自然日 0 点（按系统本地时区的日期边界），比较 `lastActiveDate` 与今天 |

喝水是**累计量**模型，不参与"连续时长"计算。

### 4.3 活动的次数模型

| 概念 | 规则 |
|---|---|
| 今日次数 | `doneToday` 累加，只用于展示，不阻断 |
| 完成动作 | "活动了" = +1 次、账本回落一级；不验证时长、不做姿态确认 |
| 达标 | 没有每日目标；活动不会因次数而停止提醒 |
| 重置 | 与喝水共用跨日边界 |

活动是**纯定时**模型：不读系统空闲时长，不做连续坐姿判断。

### 4.4 日程的事件模型

| 概念 | 规则 |
|---|---|
| 触发单位 | 一条**事件发生**（订阅 UID + 开始时刻），不是"一场会"这个概念本身 |
| 触发时刻 | `事件开始 − 前置`；前置全局一个值，默认 5 分钟 |
| 数据来源 | 用户填写的日历地址（ICS），或用户自己生成的 CalDAV 凭据；两种都只读 |
| 数据归属 | 事件属于外部日历；Barge In 只读，不写回、不改动 |
| 今日场次 | 今天剩余的事件条数，只用于展示 |
| 完成动作 | "知道了"：不写回、不计次数、账本回落一级 |
| 达标 | 没有日目标；日程永不因"完成"停止提醒 |
| 不做 | 全天事件、会议链接、参会人、结束提醒 |

日程是**外部事件驱动**模型：触发的时间点不来自本地节奏表，而来自解析后的事件列表。

### 4.5 触发来源与调度

```swift
enum SceneTrigger: Codable, Equatable {
    case rhythm(Schedule)          // 喝水：固定间隔；活动：指定时刻
    case events(leadMinutes: Int)  // 日程：来自订阅事件
}

enum Schedule {
    case interval(minutes: Int)    // 每 N 分钟
    case timesOfDay([TimeOfDay])   // 每天指定时刻
}

struct SceneRuntime {
    var isEnabled: Bool
    var trigger: SceneTrigger
    var workStart: TimeOfDay       // 只对 rhythm 生效
    var workEnd: TimeOfDay         // 只对 rhythm 生效
    var restDays: Set<Int>         // 只对 rhythm 生效
    var pausedUntil: Date?
    var isCompletedToday: Bool     // 只对喝水生效
    var events: [EventOccurrence]  // 只对 events 生效
    var handled: Set<EventKey>
    var snoozedUntil: [EventKey: Date]
}
```

- **节奏规则只作用于 `rhythm`**：`interval` 的触发点在工作时段内从 `start` 起每 N 分钟铺开，最后一个点不得越过 `end`；`timesOfDay` 的点只落在工作时段内才触发，设置界面把时段外的时刻列成琥珀色提示。
- **日程不受工作时段与休息日约束**：19:00 的晚饭、周六的日程照常提醒。事件自带时间，再套一层工作时段会让它们静默消失，这与"不静默丢弃"直接冲突。
- **免打扰对三个场景一律生效**：它是全局临时静音，不是调度规则。
- **活动出厂默认**：每天 10:30 / 14:30 / 16:30 三个指定时刻。**喝水出厂默认**：每 60 分钟。**日程出厂**：没有订阅，不触发。

**下一次触发时间（`FirePlan.next`）**：

- `rhythm`：沿用按天铺点的算法，返回 `effective` 之后的第一个点。
- `events`：在事件窗口里取第一个满足以下全部条件的事件，返回 `start − lead`：
  1. `start − lead > effective`（`effective = max(now, pausedUntil)`）；
  2. 该事件的 `(uid, start)` 不在 `handled` 里；
  3. 该事件还没开始超过 10 分钟（启动或唤醒时不为已经开完的会补弹）；
  4. 若该事件在 `snoozedUntil` 里有更晚的时刻，用那个时刻参与比较。

**驱动方式**：每个场景算出一个下一次触发时刻，`ReminderEngine` 挂一个指向最早时刻的一次性 `Timer`。以下情况重算：

- 设置变更（触发来源、工作时段、休息日、启用、前置、订阅增删）
- **订阅刷新成功或失败后**
- 系统唤醒、解锁、切回本会话（`NSWorkspace` 通知与锁屏分布式通知）
- 系统时间/时区变化（`NSSystemClockDidChange`）
- 每次触发结束后

`nextFireDates` 不落盘：启动、唤醒、改时、设置变更一律重算。把算出来的时刻存起来只会引入一份可能过期的真相。

人离开（锁屏、屏幕与系统睡眠、切到别的用户）不重算，只收起提醒层、清空队列，见 4.6 的在场门。

### 4.6 同时到点与提醒队列

三个场景独立调度，同一时刻可能都到点；日程本身也可能有多条事件挨得很近。只有一个提醒层，因此用**队列**：

- 到点即入队；去重键是 `ReminderKey`：
  - 喝水与活动：`(scene)`，每场景最多一条；
  - 日程：`(scene, eventKey)`，按事件各一条。
- 顺序：先按到点时间，再按场景声明顺序（喝水 → 活动 → 日程），同一场景内按事件开始时刻。
- 当前提醒关闭后**立即**呈现下一条；中断当前一条不会取消后面的。
- 提醒层底部显示引擎生成的"还有 N 个提醒"（不占文案槽，预设改不了）。
- 每条提醒仍用自己的激活实例、文案、音效与账本；完成 / 推迟 / 中断只作用于当前场景（日程只作用于当前事件）。
- 唤醒后只补触发时刻在 10 分钟以内的点；rhythm 每场景最多一条，日程按事件各一条但受"开始超过 10 分钟不补"约束。
- **合并呈现**不在本期：等用户需求再做。

**在场门**：到点不等于要呈现，还要人在机器前。

- `Presence` 只回答一个布尔：会话在前台、没锁屏、至少一块屏幕醒着（合盖接外接屏仍算在场）。锁屏没有官方通知，`CGSSessionScreenIsLocked` 是系统会话字典里的稳定约定、不是文档化 API；屏幕/系统睡眠、快速用户切换用 `NSWorkspace` 通知。检测失败一律按"在场"处理（fail-open）：多弹一条能被看见，少弹一条没人能诊断。
- 不在场时引擎**不采集**到点：rhythm 这一拍作废，回来等下一个点；日程事件不入队、不标记处理，回到在场时由它自己的"开始后 10 分钟"窗口重新收进来。所以三个场景的补发规则没有另开一套：节奏的"到点后 10 分钟"和日程的"开始后 10 分钟"本来就在各自的位置上，在场门只是换了它们被触发的时机。
- 人离开时立刻收起正在展示的提醒层、清空队列，不记跳过、不标记日程已处理——用户没机会响应，账本不算他跳过。
- 回到在场（解锁、唤醒、切回会话）时重算并补采集。

`ReminderQueue` 是纯函数：`dueScenes(dates:at:)` 负责排序、`enqueue(_:into:)` 负责按 `ReminderKey` 去重；`--selftest` 直接覆盖。

### 4.7 预设、强度、裂纹与档位表

```swift
enum Preset: String, Codable { case gentle, wall, shatter }
enum Intensity: String, Codable { case standard, strict }
enum CrackPattern: String, Codable { case fixed, varied }
```

**预设只有三套资源**，内置、不可安装也不可卸载，**与场景无关**：

| 预设 | 视觉做法 | 音效 | 可配置 |
|---|---|---|---|
| 温柔 `gentle` | 右上角卡片 | 单次提示音 | 仅文案 |
| 大字墙 `wall` | 满屏重复大字 | 渐强 | 强度 + 文案 |
| 碎裂 `shatter` | 满屏碎掉的深色玻璃 | 玻璃碎（一次） | 裂纹 + 文案 |

**"标准 / 强硬"不是两套预设**：它们是大字墙强度参数的两个取值，视觉与音效完全相同，差别只在档位参数。温柔预设没有强度——它的档位固定为最轻的一档。

**"固定 / 每次不同"是碎裂的裂纹参数**，只决定花纹是否每次重画：固定 = 全局唯一一套（炸点、裂纹、碎片都固定），预览与到点完全一致；每次不同 = 一次触发一套，多屏按尺寸等比缩放共用。它不改音效、时长与档位——"多难推掉"只归账本管。

**档位表由引擎持有**，预设与实例只能选强度，不能自定义数值：

| 预设 · 强度 | 能否推迟 | 中断按钮延迟 | 等级上限 |
|---|---|---|---|
| 温柔（无强度） | 允许 | 0s | 1 |
| 大字墙 · 标准 | 允许 | 0s | 2 |
| 大字墙 · 强硬 | 禁止 | 5s | 3 |
| 碎裂（无强度） | 允许 | 0s | 2 |

这张表是"越跳越硬"的安全边界：任何预设、任何副本都调不出"关掉升级"或"无限延迟"。

全屏大字墙的视觉：`大字词` 以 7° 倾角重复铺满，字号在约 0.5×–2× 之间混排，每个词各自旋转、上下偏移，行高固定，行与行之间左右错位，白色为主、青色点缀；视线落点只有中央一块半透明深色面板，用来放进度与动作。字墙按 5 组错峰闪动，每组约 2.4 秒冲到全亮一次，强调频率压得比光敏阈值低，开启系统「减弱动态效果」时保持静态。

碎裂的视觉与节奏：炸点随机落在屏面偏上、不居中，先打穿一个小孔并裂出 4–7 条带折线的主裂；裂纹从炸点缓慢爬出、越爬越快，每块楔形碎片再被随机裂口继续劈开（越靠近炸点越碎，裂缝只终止在已有裂缝上，所以有大量 T 形岔口与长短不一的局部弧）。冲击孔约 0.9 秒掉落，随后再掉一两块小碎片；裂纹长满后面板出现，玻璃停住等用户处理，但不会彻底静止——之后约每半秒开始掉一块小碎片，每块慢慢坠落约 2.5 秒，十块在面板出现后约 8 秒内掉完，遮罩上留下几个小缺口。任意动作（完成 / 推迟 / 中断）之后，面板先淡出，整片玻璃由近及远坠落（约 2 秒），遮罩随碎片一起消失、露出桌面，落完窗口才关闭。碎片本身是不透明的深色玻璃，所以遮罩能跟着坠落一起消失。开启系统「减弱动态效果」时只呈现静态裂痕，动作后立即关闭、不播坠落。

### 4.8 预设实例

预设实例是某个预设在一个场景下**被采用后的那份存在**，也就是用户在设置里看到的一张卡片。

| 规则 | 说明 |
|---|---|
| 出厂 | 每个场景三张卡：温柔、大字墙（强度取默认值标准）、碎裂（裂纹取默认值固定）；默认激活大字墙 |
| 归属 | 实例属于场景；复制出来的副本只出现在当前场景 |
| 编辑 | 改的是实例的名称、文案覆盖、强度（仅大字墙）与裂纹（仅碎裂），预设本身不动 |
| 复制 | 同场景深拷贝配置（含强度、裂纹与文案覆盖），自动命名「原名 副本」（重名时依次「原名 副本 2」），随后可改名；**复制不自动切换激活** |
| 删除 | 副本可删；内置三张不提供删除。删除正在使用的副本时回落大字墙（强度标准） |
| 激活 | 每个场景同一时刻只有一个激活实例 |
| 老存档 | 解码时缺哪张内置补哪张：追加在实例列表末尾、不激活、不动既有顺序；同一份存档补一次后幂等 |

**网格列出全部实例**，顺序就是实例顺序（内置三张在前，副本按复制先后追加）。没有「首页固定前 3 张」这回事，也就没有二级页：新副本直接出现在场景 tab 的网格末尾。

**点选只换勾选，不动顺序**：`StateStore.activate` 只改 `activeInstanceID`，网格在当前视图里保持稳定，不会在鼠标下跳位；当前使用中的卡由卡上的品牌色描边与勾标出。

### 4.9 文案槽与变量

文案是可被实例改写的唯一内容。三个槽，不同预设渲染不同的子集：

| 槽 | 内容 | 温柔 | 大字墙 | 碎裂 |
|---|---|---|---|---|
| `大字词` | 铺满屏幕的重复词 | — | ✓ | — |
| `标题` | 卡片抬头 / 碎裂面板的标题 | ✓ | — | ✓ |
| `进度模板` | 带变量的进度行 | ✓ | ✓ | ✓ |

**变量由场景提供**：

| 场景 | 变量 | 默认文案 |
|---|---|---|
| 喝水 | `{consumed}` `{target}` `{remaining}` | 大字词/标题「该喝水了」；进度「{consumed} / {target} ml」 |
| 活动 | 无 | 大字词/标题「该活动了」；进度「站起来，活动 1 分钟」 |
| 日程 | `{title}` `{start}` `{minutes}` `{location}` | 大字词/标题「{title}」；进度「{start} 开始 · 还有 {minutes} 分钟」 |

日程变量的取值规则：`{title}` 缺失时回落为「日程」；`{location}` 缺失时为空串；`{start}` 是 `HH:mm`；`{minutes}` 按呈现时刻重算，`≤ 0` 时进度模板整槽回落为「{start} 已经开始」。

**文案优先级只有两层：实例覆盖 > 场景默认。** 场景默认由场景描述提供；不单设"预设默认文案"这一层。

模板里出现当前场景不提供的变量时，**整槽回落到场景默认文案**，并在设置里标注"模板里有当前场景不提供的变量"。活动场景没有变量，任何 `{...}` 都算未知变量。

**引擎独占的文案**（预设与实例都没有对应的槽）：升级说明、完成动作标签（喝了 / 活动了 / 知道了）、"还有 N 个提醒"、可访问性标签、加载与校验错误。升级说明带场景名，例如"今天已跳过 3 次日程提醒，中断按钮延迟 10 秒"。

### 4.10 日程订阅

#### 4.10.1 订阅模型

```swift
struct Subscription: Codable, Equatable, Identifiable {
    var id: UUID
    var name: String
    var source: Source
    var isEnabled: Bool
    var lastFetchedAt: Date?
    var lastError: FeedError?

    enum Source: Codable, Equatable {
        case ics(url: URL, username: String?)                    // 密码（若有）进 Keychain
        case caldav(server: URL, username: String,               // 密码进 Keychain
                    calendars: [CalendarRef])                    // 添加时发现并选定的集合
    }
}

struct CalendarRef: Codable, Equatable {
    var href: String
    var displayName: String
}

enum FeedError: String, Codable {
    case badURL        // 不是 https，或无法解析
    case auth          // 401 / 403
    case network       // 连不上、超时、5xx
    case format        // 不是 iCalendar、CalDAV 返回非 207，或解析失败
}
```

- 可以有多个订阅，每条独立启用。
- **密码一律进 Keychain**（`kSecClassInternetPassword`，service `BargeIn.calendar`，account = 订阅 id）；`AppState` 里只留服务器地址与用户名。
- ICS 地址里的 token 属于地址本身，随 `AppState` 存 `UserDefaults`。
- 只接受 `https`；`webcal://` / `webcals://` 视为 `https://`；`http://` 直接拒绝并提示"只支持 https 地址"。理由：Basic Auth 明文过网不可接受。
- **只读边界**：CalDAV 从协议上允许写入，但 Barge In 只发 `PROPFIND` 与 `REPORT`，永不发 `PUT` / `DELETE` / `MKCALENDAR`。写操作在这个产品里没有对应功能，不存在"顺手加固"的空间。

#### 4.10.2 取数：两条传输，一颗解析器

| 传输 | 用于 | 请求 |
|---|---|---|
| `ics` | 匿名或带 Basic Auth 的日历地址 | `GET <url>`，读 body |
| `caldav` | 钉钉 / 企业微信 / 飞书 / iCloud 私有 / Fastmail / Nextcloud / Radicale | 添加时 `PROPFIND` 发现集合；刷新时对每个集合 `REPORT calendar-query` |

CalDAV 的流程（以钉钉为基准，其他服务器同构）：

1. **发现**（只在添加或「重新发现」时做）：`PROPFIND`、`Depth: 1`、body 取 `resourcetype` / `displayname` / `supported-calendar-component-set` / `getctag`。钉钉的 home set 是 `https://calendar.dingtalk.com/dav/{username}/`；其他服务器先试 `/.well-known/caldav`，再退到根路径与用户名路径。
2. **选集合**：把发现的日历列给用户勾选（默认勾主日历）。选中的 `href` 存进订阅，**刷新不再 PROPFIND**。
3. **拉事件**：对每个选中的集合发 `REPORT`，body 是 `calendar-query` + `cal:time-range`，`Depth: 1`；取 `DAV:response` 里的 `cal:calendar-data`。每个 payload 就是一段 `VCALENDAR` 文本，直接交给同一个解析器——**CalDAV 与 ICS 在解析层完全同构**。
4. **状态码**：`207` 是成功；`401` / `403` 判认证失败；返回 `200` + HTML 判格式错误（多半是被跳到了登录页）。

| 项 | 规则 |
|---|---|
| 传输 | `URLSession` + ephemeral 配置，不共享 cookie/缓存，超时 15s，跟随重定向 |
| 地址规范化 | 请求前把 `webcal://` / `webcals://` 改写成 `https://`（`URLSession` 不认这两个 scheme）；`http://` 拒绝 |
| 认证 | 只用 `Authorization: Basic base64(user:password)` 头。**不使用 URL 内嵌 `user:pass`**（RFC 7617 已不推荐，`URLSession` 也不会可靠地拿它应答 401）：粘贴的地址里带 userinfo 时，拆出来进 Keychain，地址本身去掉 |
| 请求头 | `User-Agent: BargeIn/1.0`；不手动设 `Accept-Encoding`（交给 `URLSession` 透明解压） |
| ICS 响应校验 | `Content-Type` 是 `text/calendar`（`text/plain` 也接受）；返回 HTML 判 `format` |
| CalDAV 响应校验 | 状态码 `207` + body 是能解析的 XML；`200` + HTML 判 `format` |
| 跨主机跳转 | `URLSession` 跟随时可能丢掉 `Authorization`，跳转后按目标 host 重新决定是否带凭据 |
| 触发时机 | 启动时、每 30 分钟、系统唤醒后、设置页「立即刷新」、新增订阅后 |
| 失败退避 | 连续失败后单条订阅的刷新间隔退到 4 小时，成功即恢复 30 分钟 |
| 缓存 | 每次成功把取回的日历文本写到 `Application Support/BargeIn/subscriptions/<uuid>.ics`（CalDAV 把各集合的 payload 拼成一个文件）；解析结果不落盘 |
| 离线 | 读缓存照常提醒，设置页与 popover 标注"数据可能过期（N 小时前获取）" |
| 并发 | 全局串行排队，一次只处理一条订阅的请求 |

刷新失败**不从调度里删除事件**：宁可拿过期数据提醒，也不要因为网络把一条日程静默抹掉。

#### 4.10.3 解析范围

只实现"够用"的 iCalendar 子集，全部手写在 `SceneSchedule`：

> 系统的 `Calendar.RecurrenceRule`（配合 `Calendar` 的 occurrences API）是 macOS 15+ 才有的，而本项目最低支持 macOS 14；Swift 生态里也没有能同时做"解析 + 展开"且仍在维护的库（`iCalendarParser` 只解析不展开，`RRuleSwift` 已停更，`iCalKit` 停在 2017）。因此**不引入依赖**，自己写这个子集：解析与展开加起来两百多行，覆盖面正好是"够用"。

| 项 | 支持 |
|---|---|
| 行折叠与转义 | 支持（`\n` `\,` `\;` `\\`） |
| 组件 | 只读 `VEVENT`；`VTIMEZONE` 只用 `TZID` 查系统时区 |
| 时间 | `DTSTART` 的 `TZID=` / `;VALUE=DATE` / UTC `Z` 三种形态 |
| 字段 | `UID` `SUMMARY` `DTSTART` `LOCATION` `RECURRENCE-ID` |
| 重复 | `RRULE` 的 `FREQ=DAILY/WEEKLY/MONTHLY` + `INTERVAL` + `COUNT` + `UNTIL` + `BYDAY` |
| 例外 | `EXDATE` 排除单个发生；`RECURRENCE-ID` 用覆盖体替换那一次发生 |
| 不做 | `BYSETPOS`/`BYYEARDAY`/`BYWEEKNO`、`VTODO`、`VALARM` |

- **两条传输共用这一颗解析器**：CalDAV 的 `calendar-query` 只是按 `time-range` 筛资源，服务器回来的仍然是主事件 + `RRULE`，不展开发生。所以重复事件的展开逻辑只有一份，与 ICS 完全共用。
- **`RECURRENCE-ID` 改期覆盖**：服务器会把重复事件里被单独改期/改地点的实例也作为独立 `VEVENT` 下发——`DTSTART` 是新时间，`RECURRENCE-ID` 是被替换的原始开始时刻。主事件照常展开，但覆盖体指到的那一次让位，改期后的实例按新时间出现；同一 `EventKey`（`UID` + 发生时刻）被重复下发时只留一条，不让同一次发生提醒两遍。
- **事件窗口**：只展开 `[now − 1 天, now + 8 天]` 的发生，与 `FirePlan.maxLookaheadDays` 对齐，避免每次刷新展开整个历史。
- **全天事件**（`VALUE=DATE`）直接跳过：没有具体时刻，提醒它只能是 0 点炸一条。
- **无 `UID`** 的事件按 `摘要 + 开始时刻` 合成一个键，避免同一条反复提醒。
- **时区**：`TZID` 查 `TimeZone(identifier:)`；查不到时按事件里的 UTC 偏移换算，最后的兜底是本地时区。宁可时间偏一点，也不要丢事件。

#### 4.10.4 去重与已提醒

- `EventKey = (uid, 发生时刻)`，落盘存在 `ScheduleState.handled`（`EventKey.storageKey` → 处理时间），按天清理。
- 提醒呈现后（完成 / 中断 / 推迟之外的关闭）立刻写入；已写入的不再入队，重启不重弹。
- 推迟不改 `handled`，而是写 `snoozedUntil[EventKey] = now + 5 分钟`（进程内，不落盘）。
- 刷新后事件消失：未呈现的队列条目移除，`snoozedUntil` 一并清掉；事件时间改了按新时间重排。

### 4.11 支持范围（2026-11 核实）

能不能用，取决于这家服务给不给"可被外部程序读取"的入口——两条路其中之一：一条日历地址，或一套 CalDAV 凭据。

| 服务 | 走哪条 | 用户怎么拿到凭据 |
|---|---|---|
| **钉钉** | CalDAV | 日历 → 左下「日历设置」→ 同步 → 同步到其他日历 → 其他设备 → 获取 CalDAV 账号；服务器 `calendar.dingtalk.com` |
| 企业微信 | CalDAV | 日程 → 同步至其他日历（服务器 `caldav.wecom.work`，多份第三方文档要求把给到的地址改成这个） |
| 飞书 | CalDAV（只读） | 日历设置 → 同步（服务器 `caldav.feishu.cn`） |
| 腾讯会议 | CalDAV | 日程同步设置（服务器 `cal.meeting.tencent.com`） |
| iCloud 私有日历 | CalDAV + 应用专用密码 | 服务器 `caldav.icloud.com`，账号 = Apple ID |
| iCloud 公开共享日历 | ICS | iCloud.com → 共享 → 公开日历 → 复制链接（`webcal://` 需改写） |
| Fastmail | CalDAV 或 ICS | CalDAV 用应用专用密码；或 Settings → Calendars → Publish |

## 4.12 账本与升级

### 4.12 账本与升级

**账本按场景各一份**：跳过喝水只加码喝水，不牵连活动与日程。

- `skipsToday` 存该场景当天数据，`level = min(cap, skipsToday)`，`cap` 由当前激活实例的档位决定
- **完成**一次：`skipsToday -= 1`，下限 0
- **推迟**：`skipsToday += 1`（轻违规）
- **中断**：`skipsToday += 1`（重违规，与推迟同权重）
- **次日重置**为 0

等级在档位表之上覆盖呈现参数（延迟取两者较大值）：

| level | 音效 | 推迟 | 中断按钮延迟 | 中断方式 |
|---|---|---|---|---|
| 0 | 预设值 | 档位表 | 档位表（0s / 强硬 5s） | 双击 Esc 或单击 × |
| 1 | 预设值 | 允许 | 5s | 双击 Esc 或单击 × |
| 2 | 100% 立刻 | 禁止 | 10s | 双击 Esc 或单击 × |
| 3 | 100% 立刻 | 禁止 | 10s | 双击 Esc 或按住 × 2s |

**Esc 与等级无关**：任何等级、任何预设，中断都要在 1 秒内按两次 Esc——第一次只记录，第二次才算确认，单击不生效。它同时是绕过解除延迟的逃生口：延迟还没走完时，双击 Esc 仍可立即中断。× 按钮才按等级走：level 0–2 解锁后单击即中断，level 3 需按住 2 秒。

**界面必须显式说明升级原因**：提醒层底部一行琥珀色说明，带场景名；popover 与设置窗口复用同一句文案。

## 5. 交互细节

### 5.0 设计语言

- popover 与设置共用一套令牌（`Sources/BargeIn/UI/DesignSystem.swift`）：品牌水青 `#22D3EE → #0EA5E9` 用在主操作与进度；`accent` / `warn` / `success` 三个语义色各带浅色与深色取值，组件里不写裸色值。
- 全屏提醒不复用这套安静的水色：它是一张深墨底、白/青大字铺满的墙；温柔档的材质卡片是唯一的例外。
- 字体用系统 SF Pro；popover/设置的数字与标题用 SF Rounded，大字墙用 SF Rounded Black；不打包第三方字体。
- 界面图标一律 SF Symbols，不用 emoji；图标按钮必须有可读标签。
- 品牌图形是节律脉冲：一段双峰波形，不绑定喝水场景。菜单栏 18pt 模板图与 App 图标出自 `BrandMark.swift`；仓库不存二进制图标，打包时由 `--export-icon` 生成 `AppIcon.icns`。
- 动效只表达因果：大字墙的错峰闪烁、popover 的进度动画、分段控件的选中滑动、窗口随内容变高。大字墙开启「减弱动态效果」时保持静态。
- 提醒层是全产品唯一的视觉冲突点，刻意不和任何桌面和谐共处；1 秒防误触、中断即时生效这类安全交互不因视觉简化而删减。

### 5.1 菜单栏 popover

单屏 304 宽，高度由内容决定。三个场景块都有各自的名字（12pt 半粗，位于第一行左侧）：喝水只写「喝水」，活动与日程在名字后面跟一行真实计数（`活动 今天 2 次` / `日程 今天 4 场`，10.5pt 次要色）。**喝水不显示杯数**：一次喝多少不等于一只杯子的容量，把累计毫升换算成杯数只是个假单位；水的计量全在环里。

1. **喝水区**（喝水启用时）：场景行 + 140pt 水位环。环内是大字号已喝毫升数与一行剩余（`还差 1,000 ml`，达标后写 `已达标`）；目标值只在设置里出现，环里不再重复同一个数字。**环本身就是喝水按钮**：
   - 点一下按设置里的单杯量记一杯（按下到松开不足 0.2 秒算点击）；点击与长按互斥，长按完成后松手不会再记一杯。
   - 按住 2 秒清空今日进度：按住超过 0.2 秒才进入这个样子（环内换成"松手取消"、整环转琥珀、环开始从当前进度匀速退到 0），点击不会闪；满 2 秒即清空，只清今天的毫升数，账本跳过数与免打扰都不动。提前松手或把光标移出圆外则退回原进度，不记也不清。
   - 已喝 0 ml 时长按不启动倒计时（没有可清的），但点一下照常记一杯。
   - 鼠标悬停时环内浮出 `+250 ml`，说明一下加多少；离开即隐，静态画面不留提示文字。
   - 无障碍：环是一个元素，读"今日已喝 / 目标"并带"记一杯"/"清空今日进度"两个 `accessibilityAction`，不依赖长按手势。
   - 交互状态用 `@StateObject` 存（本机 CLT 下 `@State` 宏不可用），环的显示进度 = 已喝进度 ×（1 − 按住进度）。

   环下是喝水状态行：`下次 14:30 · 18 分钟后` / `下次 明天 9:00` / `下次 周一 9:00` / `免打扰至 15:40 · 1 小时后恢复` / `今天已达标`（达标且当天没有下一拍）/ `当前设置不会触发提醒`。日期只写到明天或周X，不印月日——这行要和卡片里那一列共用宽度，写月日必被截断。再下面是喝水升级说明（跳过 > 0 且当天未达标）。
2. **活动条**（活动启用时）：图标 + "活动 今天 N 次" + 活动状态行（下次/免打扰中/今天不会提醒）+ 右侧强调态小按钮"活动了"——淡品牌色底（`accent` 16%）+ `accent` 85% 描边 + `accentText` 文字：普通灰底按钮与卡片底色只有 1.3–1.6:1 的边界，看着像不可点的说明文字；强调态边界 3.3:1（浅色）/ 4.3:1（深色），也是这一行唯一的动作；下面是活动升级说明（跳过 > 0）。
3. **日程行**（日程启用时）：图标 + "日程 今天 N 场" + 下一场（`Q4 产品评审 · 5 分钟后`，不拼绝对时间）。**没有动作按钮**——没有"完成一场会"这种事。状态行在三种情况下降级：`还没配置订阅` / `今天没有日程了` / `认证失败 · 数据可能已过期`（琥珀色）；下面是日程升级说明（跳过 > 0）。
4. **底栏**：左 `免打扰 1 小时 / 恢复提醒`（安静的文字入口，停用中转为品牌色），右 `设置…` / `退出`。免打扰是全局动作，收在底栏——整宽灰底按钮压在主动作下面的时候，没人看得见环该点。

升级说明只讲"这次怎么被对待"：`跳过 1 次，中断按钮延迟 5 秒`。它永远贴着所属场景出现（popover 的场景行下、设置里那张卡里），所以不再念一遍场景名；设置窗口复用同一句。

停用的场景整块不渲染；三个都停用时显示"提醒已全部停用"，底栏只留设置与退出。点开 popover 时激活 App 并让窗口成为 key window；再次点击图标或点外部关闭。

### 5.2 设置窗口

640 宽单窗口，标题「Barge In」，**高度跟着内容走（480–760）**：通用 tab 只有两张卡，窗口就矮下来，不再留半窗空白；内容超过上限时在窗口内滚动。顶部四个 tab：`喝水 | 活动 | 日程 | 通用`；改动即时生效，没有保存按钮。打开窗口固定落在喝水 tab。

| tab | 管什么 |
|---|---|
| 喝水 / 活动 | 场景条、提醒预设、节奏；喝水另有一张配额卡 |
| 日程 | 场景条、提醒预设、订阅列表、前置 |
| 通用 | 三个场景共用的时间（工作时段 + 休息日，仅对喝水与活动生效）、开机自启、隐私说明 |

**场景 tab**

滚动区自上而下：

| 区块 | 内容 |
|---|---|
| 场景条 | 一句说明 + `启用` 开关。场景名只在 tab 上出现一次；停用后仍可在此页编辑，只是不调度 |
| 提醒预设 | 三列网格，列出该场景的全部实例（顺序即实例顺序，见 4.8）。每张卡：66pt 的**呈现微缩图**、名称（副本名自带「副本」后缀）、一句说明；使用中的卡是品牌色描边 + 淡底 + 勾。网格下方是使用中那张卡的一行动作 `编辑文案 / 预览 / 复制 / 删除`（内置卡没有删除），再下面是当前使用卡片的升级说明 |
| 节奏 | 固定间隔 / 指定时刻二选一；间隔步进（5–240 分钟），或时刻列表；空列表与时段外时刻给行内琥珀提示 |
| 喝水（仅喝水 tab） | 日目标、单杯量的步进。单杯量是"点一下环记多少"的增量，不换算成杯数 |

**微缩图**是设置页唯一上色的地方（`PresetThumbnail`，`Sources/BargeIn/UI/PresetThumbnail.swift`）：大字墙铺三行重复大字并逐行淡出；温柔是浅色屏幕上右上角一张小卡片，深色外观下屏幕跟着变深；碎裂是暗屏上从中心裂开的细线加标题。图里的字取该场景的默认文案，日程的 `{title}` 用样例事件名填。它的意义是把"提醒长什么样"直接摆在选择处——图标加一句描述说不清这件事。

**指定时刻**的每一行是一整个列表：整组包在一层描边容器里，行间用分隔线连起来；行内左侧是时间（13pt 圆体 + 下拉符号，点开时间面板），右侧是安静的删除入口（`ConfirmDeleteButton(form: .quiet)`）。第一下点成「确认删除」，第二下才真的删。时间与删除同属一行，不会出现中间空一大截的割裂感。

**编辑**在动作行之后展开（不再插到被编辑卡片所在的那一行）：

1. **名称**（只有副本有这一行）：卡片名。内置三张不提供——它们的名字代表预设本身。
2. **强度**（只有大字墙有这一行）：`标准 | 强硬` 分段；紧跟一行说明。
3. **裂纹**（只有碎裂有这一行）：`固定 | 每次不同` 分段；紧跟一行说明。
4. 该预设渲染的文案槽：大字墙是 `大字词` + `进度模板`，温柔与碎裂是 `标题` + `进度模板`。
5. 可用变量提示；活动场景显示"这个场景的文案不支持变量"。
6. 右上角 `恢复默认文案`——只重置文案覆盖，不重置强度、裂纹与名称。

名称、强度、裂纹与文案都即时生效，即时作用于预览与真实提醒。改名写到 `StateStore.rename`：首尾空白去掉，清空或只剩空白视为放弃。

**动作行作用于当前使用中的那张卡**：点卡片即切换激活（和以前一样），编辑 / 预览 / 复制 / 删除跟着切换过去。预览按这张卡自己的预设、强度、裂纹与文案覆盖呈现一次，升级等级用该场景当前的跳过次数；预览不切换激活项、不写进度与账本、不动调度，任何动作只关闭。日程卡的预览用一个占位事件（"预览 · 10:30 开始"），不需要订阅。

**日程 tab** 与喝水/活动是同一套骨架，只把「节奏」与水量卡换成订阅与前置：

| 区块 | 内容 |
|---|---|
| 订阅 | 标题右侧 `N 个来源 · 最近同步时间` + `立即刷新`；列表每行：状态点、名称、`类型 · 最近同步`（失败时琥珀色写原因）、`今日 N 场 ›`、启停开关、删除入口。点 `今日 N 场` 在该行正下方展开今日事件列表（时间 + 标题 + 地点；已过去的条目降一档对比度、面板每分钟重算；空态「今天没有日程」；同时只展开一条；数据来自已解析的事件，不重新联网）；下方虚线 `添加订阅`；卡底一行"只读：Barge In 只做读取，从不写回，也不上传任何内容" |
| 前置 | 事件开始前 N 分钟（1–60，步进 1）；卡底说明"全天事件不提醒；已经开始超过 10 分钟的事件不再补提醒；重复事件按规则展开"。卡头不再重复当前值 |

日程 tab **没有「节奏」卡**：节奏就是日历本身。卡底一行说明"日程不受工作时段与休息日约束，免打扰仍然生效"。空订阅态下，「提醒预设」与「前置」照常可见，只是一个都不会触发。添加订阅的表单与编辑面板用同一套输入框皮肤。

**通用 tab**：时间卡（工作时段起止、休息日 7 个胶囊、时段长度、结束早于开始的行内提示、"喝水与活动共用这套时间"说明）、通用卡（开机自启，附一句"登录后在菜单栏静默启动，不打开窗口"），卡下方一行"零权限 · 数据只保存在本机；日程订阅是唯一联网功能，只读"。

**其余交互**：时间输入统一用自绘 `TimePicker`（`Sources/BargeIn/UI/TimePicker.swift`）：收起态是 24 小时制 `HH:mm`（`bordered: false` 时进入列表行，不画胶囊边框），点开是「时 / 分」6 列网格；分按 5 分钟步长，当前值不是 5 的倍数时一并列进可选集。单击即改、即时生效。`Esc` 逐级退：编辑面板展开时先收起，否则关闭设置窗口。

底栏固定：状态点 + 最近一次提醒（跨场景取最早，带场景名，如 `下一次提醒 · 喝水 明天 9:00`；日程取最近一场事件）、免打扰/全部停用/不会触发各有文案，右侧"改动即时生效"。底栏随设置改动即时刷新。

窗口尺寸由 `SettingsView.onContentResize` 通知 `SettingsWindowController.fitToContent()`：切换 tab、展开编辑面板、展开订阅表单都会重新贴合，窗口只向下长，标题栏留在原处（最小 `480`、最大 `760`）。

### 5.3 首次启动

首次启动打开设置窗口，只做一次选择：温柔 / 大字墙 / 碎裂三张卡（带微缩图、不显示动作行与强度控件），默认选中大字墙、强度取默认值标准。

**窗口一打开就算看过首屏**（`hasOnboarded = true` 立即落盘）：用户直接关窗、`⌘Q`、强退、或者根本没点「就用这个」，首屏都不会再来第二次——关掉窗口等于采用默认值（大字墙·标准）。首屏只出现在"这份存档里没有首屏记录"这一种情况。

点「就用这个」之后：

1. 这次选择**同时落到三个场景**的激活实例（选温柔则都温柔；选大字墙则都大字墙·标准）。
2. **立即按喝水场景真实呈现一次预览**——视觉、音效、该档位的延迟行为全都在。强硬档在预览里同样要等 5 秒才能关。
3. 预览里任何动作只关闭：不写状态、不记账、不动调度。双击 Esc 仍是通用逃生口。
4. 预览里显示一行"这是预览"的标识。
5. 预览关闭后**关闭设置窗口，只剩菜单栏**。

日程不参与引导：出厂停用，用户第一次进日程 tab 添加订阅后才有数据。

### 5.4 提醒层

- 每个 `NSScreen` 一个 `NSPanel`，`level = .screenSaver`，覆盖菜单栏与 Dock。
- `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary, .stationary, .ignoresCycle]`，切 Space 不丢失。
- 全屏固定深色外观，不跟随系统浅色主题；卡片跟随系统外观。
- **全屏**：满屏重复的 `大字词` 大字墙，中央半透明深色面板承放进度、动作与升级说明。
- **卡片**（温柔）：右上角 360×260 的 `.regularMaterial` 小面板，标题、进度、动作竖排。
- **碎裂**：整屏是一块不透明的深色玻璃，裂纹与碎片就是遮罩本身；中央深色面板承放标题、进度与动作。等用户处理期间，约每半秒开始掉一块小碎片，共十块（遮罩上留下小缺口），碎块本身提亮一点，否则深色碎片在深色玻璃上看不出来。动作后整片玻璃由近及远坠落（约 2 秒），遮罩随碎片消失、露出桌面，落完才关窗。
- **文案来源**：提醒层里所有可改写的文字都取自当前场景激活实例的槽渲染；升级说明、完成动作标签、"还有 N 个提醒"、可访问性标签由引擎生成，实例改不动。
- 动作：
  - **完成**（点按钮，或 1 秒内连按两次 `Enter`）→ 记账并关闭当前这条；喝水 +杯量，活动 +1 次，日程只记一次「知道了」
  - **推迟 5 分钟** → 关面板；rhythm 把当前场景下一次触发提前到 5 分钟后（进程内覆盖），日程把这条事件记进 `snoozedUntil`（5 分钟后再提醒一次，即便事件已经开始）；不允许推迟时不显示
  - **中断**（快速双击 `Esc` 或右上 `×`）→ 立刻关闭，零等待；`level 3` 下单击 `Esc` 无效，需双击 `Esc` 或按住 `×` 2 秒
- **队列**：关闭当前这条后，如果队列里还有下一条，立即呈现；下一条仍走自己的预设与档位。提醒层底部显示"还有 N 个提醒"。中断当前一条不会取消后面的。碎裂的退场要播完坠落（约 2 秒），队列里的下一条等它播完再出现，不插进坠落动画里。
- **防误触**：覆盖层出现后 1 秒内所有按钮不响应；宿主视图 `acceptsFirstMouse` 恒为 true。碎裂在裂纹长满、面板出现（约 2.25 秒）之前连 Esc / Enter 都不响应——用户还没看到任何东西，不该被一个按键关掉。
- **延迟只锁中断**：等级 1/2 的延迟只作用在中断路径；"完成"和"推迟"在 1 秒防误触后即可用。
- **键盘与焦点**：展示时 `NSApp.activate()` 激活自身、面板 `makeKeyAndOrderFront` 成为 key window；`Esc` 与 `Enter` 都由 App 级 `NSEvent` 本地监听处理。`Enter` 与 `Esc` 各记一份双击时间窗。队列里连续呈现时，不把前台还给原 App 又抢回来；最后一条关闭后才还原。
- 可访问性：大字墙对 VoiceOver 读作一个完整的 `大字词`；按钮都有中文标签；关闭键带 `help` 说明。
- 中断永远即时生效：不拦截键盘、不阻止切换 App、不阻止强退。强度只体现在"下次更硬"，不体现在"这次逃不掉"。

## 6. 扩展点

v3 只留四个缝：

| 缝 | 位置 | 加东西的成本 |
|---|---|---|
| 新的视觉做法（= 新预设） | `Preset` 加一个 `case` + 一个布局 + 音效 + 档位表加一行 | 一个枚举、一个视图、一张表，不涉及实例、场景与账本 |
| 新的可配置属性（如字号） | 预设声明该属性 + 引擎给合法取值 + 编辑器加一个控件 | 引擎内部 |
| 新的场景 | `SceneID` 加一个 case + 一个场景模块（状态 + 描述）+ `AppState` 聚合 + 设置页两处文案 | 预设、实例、账本、队列的结构不动 |
| 新的取数方式（Graph / 飞书开放平台等） | `Subscription.Source` 加一个 case + 一个传输实现 + 解析不变 | 只换 `SceneSchedule` 的取数层，事件模型与调度不动 |

**明确不做**：场景的插件注册、清单文件、目录扫描；合并呈现与优先级；预设的安装/卸载；市场；用户自定义槽与 schema；声明式布局语言；素材运行时；CalDAV 的写操作与增量同步。

## 7. 持久化

单个 `Codable` 结构，一个 `UserDefaults` key（`"AppState"`），无数据库、无文件迁移：

```swift
struct AppState: Codable, Equatable {
    var waterConfig: SceneConfig
    var activityConfig: SceneConfig
    var scheduleConfig: SceneConfig

    var water: WaterState
    var activity: ActivityState
    var schedule: ScheduleState      // 订阅元数据、已提醒的 EventKey、最近事件数

    var workStart: TimeOfDay
    var workEnd: TimeOfDay
    var restDays: Set<Int>
    var pausedUntil: Date?
    var lastActiveDate: Date
    var hasOnboarded: Bool
}
```

- 解码逐字段容错：每个持久化类型都有自写的 `init(from:)`，字段缺失、类型不符、枚举 `rawValue` 不认识时只让那一个字段回默认值，不牵连同一条记录的其它字段；数组按条容错，一条坏数据只丢那一条。顶层同理：某个场景整块读不出来只回该场景出厂配置，同一次存档里的其它场景与进度照留。
- 场景身份字段（`SceneConfig.trigger`、`PresetInstance.preset`、`Subscription.kind`/`url`）不猜默认值：读不出来就整块（或整条）回出厂，避免"读成另一个场景/另一套预设"的静默错配。
- 连逐字段容错都救不回来的存档（比如完全不是 JSON）：先把原始 bytes 另存到 `Application Support/BargeIn/state-unreadable-<时间>.json`，再用出厂值启动，并在日志里说明。**任何情况下都不静默丢档。**
- 场景配置解码后 `normalize()`：空实例列表回出厂三张卡，缺哪张内置补哪张（追加末尾、不激活、幂等），激活项丢了回大字墙。
- 存档域：打包版是 `com.bargein.app`（`UserDefaults.standard`）；`swift run` 跑的是裸二进制、没有 bundle id，会落到以进程名命名的另一个域，所以无 bundle 时统一回 `com.bargein.app`，开发期与安装版共用同一份存档。
- **`AppState` 里不存密码、不存 `.ics` 原文、不存下一次触发时刻、不存队列、不存 `snoozedUntil`**。密码在 Keychain，`.ics` 在 `Application Support/BargeIn/subscriptions/`，其余都是运行时状态。

## 8. 边界与异常

| 场景 | 处理 |
|---|---|
| 三个场景同时到点 | 都入队；先到先呈现，关闭当前后立即呈现下一条；提醒层显示"还有 N 个"；不静默丢弃 |
| 一个场景停用 | 该场景不调度、不入队、popover 整块不渲染；其余场景不受影响 |
| 三个场景都停用 | 调度返回空；popover 显示"提醒已全部停用"；设置底栏同文案 |
| 睡眠后唤醒，`nextFireDates` 已过 | 只补触发时刻距今 10 分钟以内的点；rhythm 每场景最多一条，日程按事件各一条且开始不超过 10 分钟 |
| 睡眠跨过工作时段结束 | rhythm 不触发，重排到次日时段开始；日程照常 |
| 锁屏 / 屏幕睡眠 / 切到别的用户时到点 | 不采集、不呈现：rhythm 这一拍作废，回来等下一个点；日程回到在场后按"开始后 10 分钟"重新收 |
| 提醒展示中锁屏、合盖或切走用户 | 立刻收起面板，不记跳过、不标记日程已处理；日程在 10 分钟内回到在场会再响一次 |
| 锁屏一整夜 / 睡眠跨过多次触发点 | 离开期间的触发点全部作废，回到在场后从当前时刻重排 |
| 拿不到锁屏或屏幕状态 | 按在场处理（fail-open）：照常提醒，不因检测失败静默消失 |
| 系统时间/时区跳变 | 监听 `NSSystemClockDidChange`，先补再重排 |
| 跨日发生在提醒展示期间 | 面板正常关闭；状态重置在下次读取时懒执行 |
| 已完成当日喝水目标 | 喝水调度返回 `nil`（次日重排）；活动与日程继续 |
| 不在工作时段 / 休息日 | 喝水与活动不调度；**日程照常提醒** |
| 免打扰中 | 免打扰优先于三个场景的调度；`pausedUntil` 到期后重算；免打扰时丢弃进程内推迟 |
| 提醒已在展示，另一场景又到点 | 新的一条入队；当前关闭后立即呈现；同一 `ReminderKey` 不重复入队 |
| 队列里的一条被中断 | 只为当前场景记一次跳过；后续条目照常呈现 |
| 多显示器热插拔 | 监听 `NSApplication.didChangeScreenParametersNotification`，重建面板集合 |
| 全屏 Space 中触发 | 面板以 `.fullScreenAuxiliary` 加入当前 Space |
| 勿扰模式开启 | 自绘窗口不受 DND 影响；音效受系统音量约束，不主动改系统音量 |
| 提醒间隔设得过小 | 设置界面约束下限 5 分钟 |
| 提醒展示时退出 App | 不做拦截，正常退出；状态已落盘 |
| 单杯量 > 日目标 | 允许，完成一次即达标 |
| 账户地址不是 https | 不保存，行内提示"只支持 https 地址" |
| CalDAV 账号或密码错 | 发现阶段就 401 → 提示"账号或密码不对"，不保存这条订阅 |
| CalDAV 发现不到任何日历 | 提示"这个账户下没有可读的日历"，不保存 |
| CalDAV 服务器不认常规 home set | 依次试 `/.well-known/caldav`、根路径、`/dav/{username}/`；都失败则提示"这台服务器需要完整发现，本期不支持" |
| 某个集合 REPORT 失败 | 只有这个集合降级为缓存，同账户其他集合照常；错误按集合记录 |
| 用户取消勾选某个日历 | 该集合的事件立即失效；队列里属于它的条目移除 |
| 在钉钉里重置了 CalDAV 密码 | 旧凭据 401 → 提示重新生成并改这一条订阅的密码 |
| 订阅地址拉不到 / 超时 | 用上次缓存继续提醒；设置与 popover 标注"数据可能过期（N 小时前）"；退避到 4 小时 |
| 订阅 401 / 403 | 标"认证失败，检查用户名或密码"；不改缓存、不停调度；用户可改凭据后立即刷新 |
| 订阅返回的不是 iCalendar | 标"格式无法解析"；保留上一次成功的缓存 |
| 订阅里没有任何事件 | 正常；popover 显示"今天没有日程了" |
| 事件没有标题 | `{title}` 回落为「日程」 |
| 事件是全天事件 | 跳过，不提醒 |
| 事件已经开始超过 10 分钟 | 不补提醒（启动、唤醒、刷新都按这条） |
| 两个事件相隔 5 分钟 | 各自入队，逐条呈现，"还有 N 个"正确 |
| 队列里的日程提醒还没呈现，事件被删了 | 刷新后从队列移除，`snoozedUntil` 一并清掉 |
| 队列里的日程提醒还没呈现，事件被改时间 | 按新时间重排；旧键作废 |
| 推迟后事件已经开始 | 仍在 5 分钟后提醒一次，进度模板回落为「{start} 已经开始」 |
| 删除正在使用的订阅 | 该订阅的事件立即失效；队列里属于它的事件移除；不允许删除正在拉取中的条目（等这次结束） |
| 订阅 URL 里带 token | 视为凭据本身，随 `AppState` 存 `UserDefaults`；不进日志、不进错误文案 |
| 拉取期间用户删掉该订阅 | 本次结果丢弃，不写缓存 |
| `TZID` 查不到 | 用事件自带 UTC 偏移；再不行按本地时区 |
| 复制一张预设实例 | 深拷贝强度、裂纹与文案覆盖，自动命名并可改名；**不自动切换激活** |
| 删除非当前使用的副本 | 直接移除该卡 |
| 删除正在使用的副本 | 移除，激活回落到该场景的大字墙（强度标准） |
| 文案模板含当前场景不提供的变量 | 整槽回落到场景默认文案，设置里标注 |
| 预设越积越多（复制、改名） | 场景 tab 的网格列出全部卡片并随内容滚动；点选只换勾选，不重排 |
| 旧数据没有场景字段 / 没有 `trigger` | 该场景整块回出厂，同一次存档里的其它场景与进度照留 |
| 存档里一张卡或一条订阅读不出来 | 只丢那一条；内置卡由 `normalize()` 补回，其余卡片与订阅不动 |
| 整份存档完全读不出来 | 原始 bytes 另存 `Application Support/BargeIn/state-unreadable-*.json`，用出厂值启动，不清空、不静默 |

## 9. 工程与构建

**当前机器只有 Command Line Tools（`xcode-select -p` → `/Library/Developer/CommandLineTools`），没有完整 Xcode。** 因此不使用 `.xcodeproj`，改用 SwiftPM 构建 + 脚本组装 `.app`。

```
Package.swift            // BargeInCore / SceneWater / SceneActivity / SceneSchedule / BargeIn
Sources/BargeInCore/     // 场景无关的引擎
Sources/SceneWater/      // 喝水场景
Sources/SceneActivity/   // 活动场景
Sources/SceneSchedule/   // 日程：ICS 解析、RRULE 展开、事件模型
Sources/BargeIn/         // App 层：状态聚合、订阅拉取与缓存、Keychain、UI、提醒层、自检
Info.plist
scripts/bundle.sh        // 组装 Barge In.app
Makefile                 // make run / make app
```

- **SwiftUI 属性包装器宏（`@State`、`@Binding`、`@Environment`）在 CLT 下不可用**：界面里所有可变状态一律用 `@Observable` 类，绑定用 `Binding(get:set:)` 手工构造。
- `make app`：`swift build -c release` → 组装 `Barge In.app/Contents/{MacOS,Resources,Info.plist}` → 调 `--export-icon` 生成 `Contents/Resources/AppIcon.icns` → `codesign -s -`（ad-hoc）。
- 五个开发期开关：`--selftest` 跑不依赖 UI 的检查，`--demo` 立即弹一次喝水提醒，`--snapshot <dir>` 把 popover / 设置 / 提醒层离屏渲染成 PNG，`--export-icon <dir>` 生成 iconset / icns 与菜单栏图预览，`--calendar-probe` 只取一次并把解析结果打到 stdout：`--calendar-probe ics <url>` 或 `--calendar-probe caldav <server> <username> [--discover]`（排查订阅用，密码从环境变量读，不落盘）。
- `Info.plist` 关键项：`LSUIElement=true`、`CFBundleIdentifier`、`LSMinimumSystemVersion`、`CFBundleIconFile`。
- **不启用 App Sandbox**（SwiftPM + 脚本分发的现状），因此 `URLSession` 出站不需要额外 entitlement；凭据走 Keychain，不需要用户授权弹窗。ATS 默认只允许 https，与"只接受 https 订阅"一致，不加例外。
- 正式分发需 Developer ID 证书 + 公证，放到发布阶段处理，不在本期代码范围内。

**权限清单：仍然零权限。** 不使用 `UNUserNotificationCenter`、不使用辅助功能、不使用屏幕录制、不使用 Apple Events。日程场景新增的只有出站 HTTPS GET，不是系统权限。

## 10. 开源与付费的代码留位

- 仓库整体 MIT，全部代码公开、功能全开，**代码里不存在任何付费判断**。
- 未来的付费内容是**预设**（视觉做法、音效、文案），不是代码能力；届时从官网单独分发，不进入公开仓库。
- v3 仍然只有内置三套预设：不做市场、不做下载、不做安装卸载、不做 manifest 与目录扫描。
- 不建空目录、不预埋格式、不写未使用的分支。

## 11. 竞争力与可行性

**竞争力**

- 唯一的结构性空白：**提醒呈现层可实例化、可改文案、可复制**。竞品的硬阻断全是设置里的开关，没人把"提醒长什么样"当内容做。
- 喝水 + 活动 + 日程三者合体，且**日历年是反过来用的**：竞品用日历决定"什么时候别打扰"，Barge In 用日历决定"什么时候该把你拽出来"。
- **仍然零权限**：出站 HTTPS GET 不是系统权限，不需要用户到系统设置里点允许。
- 代价必须承认：日程是第一个联网功能，破了"零网络"的卖点，必须靠"只读、可选、默认关、可自证"把它变成可解释的例外（[ADR-0001](adr/0001-network-for-calendar-subscriptions.md)）。此外代码可被 fork，护城河是内容质量与更新节奏。

**可行性**

- 天花板可见：$5k/月是最贵档位、闭源、口碑驱动的头部产品的量级；开源 + 内容收费应低于此。复杂度必须被严格约束。
- 技术风险集中在日程：ICS 解析与 RRULE 展开必须自己写，CalDAV 各家服务器的发现行为差异是主要不确定项（钉钉的 home set 形态已从实践确认，其余服务以上线前的实测为准）。
- 最大风险不是技术，是**默认值**：这个品类的用户在第一周就会关掉提醒。因此"大字墙 · 标准"必须是能打断心流的，活动的出厂节奏不能出厂就每天连弹，日程出厂必须停用。
