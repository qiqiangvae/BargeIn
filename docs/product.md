## 1. 一句话定位

**Barge In 是一个反内耗的 macOS 打断工具**：常驻菜单栏，平时不存在；你被手头的工作吸进去的时候，它用一套能打断心流的提醒呈现把你拽出来，免得你漏掉别的正事——该喝水、该起身、该进下一场会、该去点外卖。

这里的「内耗」只有一个意思：**手头这件事把你别的正事挤掉**。它不是精神内耗，也不是职场内卷。

## 2. 它是什么，不是什么

| 是 | 不是 |
|---|---|
| 一个**上下文切换器**——唯一职责是在对的时刻把你从当前工作里物理性地拉出来 | 一个健康数据看板 |
| 一个**提醒呈现可配置**的引擎：三套预设、可选强度、每个场景下都可改文案、可复制 | 又一个角标显示"该喝水了"的通知工具 |
| 一个**强度由预设决定**的工具：要更狠就换预设或改强度，产品不根据跳过次数自动加码 | 一个会自动升级、越跳越狠的惩罚系统 |
| 一个**四场景**的打断工具：喝水、活动、日程、闹钟各有一套调度与账本（记录），同时到点也不互相吞掉 | 一个需要你手动切换场景的番茄钟 |
| 一个用**你已有的日历**决定"什么时候该打断你"的工具 | 一个日历客户端：不新建事件、不改事件、不写回 |
| 一个能用**你自己定下的时刻**（点外卖、交周报）拽你出来的工具 | 一个待办清单：没有勾选完成、截止日、优先级与历史 |
| 一个**零系统权限**的本地小工具，联网只在你主动开启日历时发生 | 需要账号、云同步、多端的服务 |

## 3. 需求来源与证据

### 3.1 本项目的第一手动机

> "太温柔了。我知道我要喝水，但我就是停不下来工作。"

这句话定义了产品的全部：**用户不是不知道，是做不到**。系统通知横幅、角标、轻轻一声"叮"——对这种状态的人等于零。所以起点不能温和。

### 3.2 多场景的动机

喝水与活动是两种不同的身体节律：喝水是**累计量**（今天喝到多少），活动是**定时**（到点起来舒展）。把两件事塞进一个提醒会互相污染——喝水的"第几杯"对活动没有意义，活动的"今天几次"也不该阻断喝水。所以它们是两个场景：各自调度、各自记录、各自预设实例，共用一套提醒呈现。

**日程是第三种**：它的时刻不来自本地节奏，而来自**用户已经维护好的日历**。它解决的是"我自己排的会，我照样会错过、会拖着不去"——而 Barge In 恰好有一个日历 App 给不了的东西：一个能打断心流的呈现。

**闹钟是第四种**：它的时刻同样不来自本地节奏，也不来自外部日历，而是**用户当场许下的一个时刻**——"11:30 点外卖""这周五 16:00 交周报"。它解决的是第三句话："我自己设的提醒，系统弹一条横幅，我正忙就划掉了。" 系统闹钟能叫醒你，但叫不醒一个正在写代码的人；这正是产品立论的原点。

四条链路的分工要一句话说清：喝水与活动是**已经定好的节奏**，日程是**别人排进你日历的事**，闹钟是**你自己临时定下的事**——四者等权，都是"被工作挤掉的正事"。

同时到点不能靠"先到先得、另一个作废"：静默丢掉一条提醒是这个产品最不该做的事。v0.2 用**提醒队列**——每条都呈现，关闭一条立刻呈现下一条。

### 3.3 竞品侧的证据（详见 [competitor-scan.md](competitor-scan.md)）

| 事实 | 对产品的含义 |
|---|---|
| 硬阻断手段早已存在（`enforce`、整屏锁定、延迟解除、Strict Mode），但全是设置里的开关 | 做"更硬"不构成差异化；把"强度"做成一等公民才构成 |
| 没有任何竞品把提醒呈现层做成可更换、可配置的内容 | **最大的结构性空白**：呈现层本身就是商品 |
| 该品类头部产品把"不打扰"当政治正确（Smart Pause、自动避让） | "能打断心流"在英文区是逆风位，但也是未被占据的位置 |
| **日历在这个品类里只被用来避让**（Time Out 按日历推迟、会议期间不提醒） | 反过来用：用日历决定**什么时候该打断**，这是没人占的位置 |
| 喝水与休息分属两个品类，无人合体 | 先把喝水与活动做成两个场景，再逐个加 |
| 系统提醒在"正在工作"面前等于不存在 | 用户自己定下的时刻也要接进打断式呈现，这是第四个场景 |
| 该品类用户的两个真实抱怨同时存在："太温柔我没注意到"与"我开始对这个 App 产生敌意" | 只收下前者作为产品约束（"太温柔"是全品类的共识失败）；后者不做强度的上限，也不靠自动加码去消化——强度由用户选，产品不反制，见 §6 原则 1、原则 7 |

## 4. 目标用户

**主用户**

- 每天在 Mac 前连续工作 6–10 小时的个人用户：程序员、设计师、写作者
- 知道自己该喝水、该起来活动、该进下一场会、该去做某件正事，也认同这件事
- **试过 1–3 个提醒 App，都在第一周把它关掉或删掉了**
- 对"被管理"敏感，对"被通知识别"极其敏感；讨厌劫持键盘、讨厌权限弹窗
- 四个场景等权：它们都是"被工作挤掉的正事"，不存在哪个场景更重要。日程场景对日历里有会的人更有用，但"日历是 ta 的工作表"不是主用户的准入门槛——不用日历的人仍然可以用喝水、活动与闹钟

**不是目标用户**

- 找健康数据、体能记录、体检建议的人
- 团队/公司（不做管理台、不做合规）
- 需要 Barge In 自己做日历同步、在 App 里编辑日程的人
- 需要待办清单（勾选、截止日、优先级、历史）的人

## 5. 价值主张

对上面这类用户，Barge In 提供四件别人没有同时给的东西：

1. **能打断心流的默认档**——出厂默认就是大字墙 · 标准：满屏重复大字 + 渐强音，不是一条随时被划走的横幅
2. **提醒长什么样、说什么、有多难推掉，由你决定**——三套预设（卡片 / 满屏大字 / 满屏碎裂），大字墙可选标准或强硬，碎裂每次重新生成花纹；强度是大字墙独有的可配置项，和文案一样由你自己改；每个场景的每张卡片都能改文案、复制一份拿去改
3. **四个场景互不吞掉**——喝水、活动、日程、闹钟各自调度；日程直接吃你已有的日历，闹钟接住你临时定下的时刻，两个会挨着也能逐条呈现
4. **你自己的时刻也算数**——"点外卖"这种没人会替你排进日历的事，也能用同一套呈现把你拽出来

## 6. 产品原则

1. **强打断与视觉冲突不设上限**。提醒能有多狠，这个方向没有天花板：强度、冲突、压迫感是要被推到极致的**目标**，不是需要被克制的风险。产品的失败模式只有一条——太温柔，没把人拽出来。因此任何呈现创意都合理，形式与尺度不受限制：遮挡、剥夺、跟随、悬置、触觉、声音、时间渐变、叙事（满屏碎裂、涨上来的水）。"是不是太过了"不是该问的问题。

   **创意评审口径**：以后评估任何提醒形式，只问两句——**它能不能更有效地把人从工作里拽出来，以及它怎么实现**。不问"会不会太打扰""用户会不会反感""仪式感会不会衰减""会不会把用户赶走"；这些不是产品顾虑，是把产品拉回起点的借口。唯一可以否掉一个创意的理由是**事实上做不到**（平台能力）或**破了零权限/不劫持系统**（见原则 3、原则 4），那是工程事实，不是审美退让。

   **边界**：本原则管的是呈现强度与创意，不解除原则 3、4；调度频率也不设产品级上限，靠默认值与用户自己的开关，不靠限流。

2. **默认值就是产品**。用户可以关掉一切，但出厂状态必须是能起作用的。日程与闹钟例外地出厂停用：没有数据就没有意义。

3. **不劫持系统**。不拦键盘、不改系统音量、不阻止切 App、不阻止强退。提醒层展示时会短暂取得键盘焦点（双击 Esc 可中断），关闭后把前台还给原 App；强度来自预设本身，不来自"这次逃不掉"。

4. **零权限**。不用通知中心、不用辅助功能、不用屏幕录制、不用 Apple Events。联网不是权限。

5. **一次交互一个动作**。完成、推迟、中断，三选一，不需要学习。队列里的每一条仍然是这条规则。

6. **默认不联网，数据只在本机**。只有两个例外，都只读、都不上传任何内容：**日程订阅**（可选、默认关，只访问用户自己填的地址）与**更新检查**（默认开、可关闭，只向 GitHub 问一次最新版本号与发布说明）。没有账号体系、没有遥测。

7. **不自动加码**。强度属于预设实例，和文案覆盖同级；产品不根据跳过次数、完成次数或任何记录改变呈现，也不设"越跳越硬"的机制。账本只记录。要更狠，换预设或改强度。

8. **不静默丢弃**。已到点且用户在场时，不静默丢弃：多场景同时到点逐条呈现；网络断了就按缓存提醒并明说数据可能过期。达标静默、免打扰、不在场、日程"开始后 10 分钟"、一次性闹钟过期是明确的例外，不在此列。

9. **场景是对称的**。四个场景都有启用开关、预设实例、账本与完成动作；"触发来源"不同，待遇不降级。

10. **通用时间只有一套**。工作时段与休息日是全部场景共用的；喝水、活动、闹钟受它约束，日程因为事件自带时间而豁免。不按场景各写一套时间规则；与它冲突的闹钟在界面上标成无效并写明原因，不静默吞掉。

## 7. 功能全景

### v0.1（首个版本，仅喝水）

| 功能 | 说明 |
|---|---|
| 菜单栏常驻 | 无 Dock 图标、无主窗口，popover 查看进度与操作 |
| 喝水配额 | 日目标、单杯量、今日进度、达标即静默、自然日重置 |
| 三种结束方式 | 完成（+一杯）/ 推迟 5 分钟 / 中断（即时生效） |
| 三套呈现预设 | 温柔（右上角卡片 + 提示音）/ 大字墙（满屏重复大字 + 渐强音）/ 碎裂（满屏碎玻璃 + 玻璃碎音）；大字墙可选强度，碎裂每次随机 |
| 账本 | 记录当天的进度、完成次数与跳过次数；不改变下一次提醒，次日归零 |
| 调度 | 固定间隔 / 每天指定时刻 / 工作时段 / 休息日 |
| 设置窗口 | 单窗口、分 tab、即时生效，每张预设卡都能单独预览 |
| 兜底 | 免打扰 1 小时、开机自启 |

### v0.1.1（预设实例）

- 每个场景出厂三张卡：温柔、大字墙（强度默认标准）、碎裂，默认激活大字墙
- 卡片可编辑：强度（仅大字墙）与文案槽，带可用变量提示与"恢复默认文案"
- 卡片可复制：同场景深拷贝一份；副本可删，内置三张不可删
- 首次启动：三张卡里选一张（默认大字墙 · 标准），点"就用这个"后立即真实呈现一次预览

### v0.2（多场景 + 活动）

| 功能 | 说明 |
|---|---|
| 两个场景 | 喝水（累计量、达标静默）与活动（纯定时、起身舒展、无配额） |
| 按场景配置 | 每个场景有自己的调度、预设实例、记录、启用开关；工作时段、休息日、免打扰全局共享 |
| 提醒队列 | 同时到点逐条呈现；每场景最多一条待处理；提醒层显示"还有 N 个提醒" |
| popover 双场景 | 水位环 + 活动条；停用的场景整块隐藏 |
| 分包 | 场景无关引擎、喝水、活动、App 层四个 SwiftPM target |

### v0.3（日程）

| 功能 | 说明 |
|---|---|
| 第三个场景 | 日程：订阅你已有的日历，事件**开始前 N 分钟**（默认 5）把你拽出来 |
| 只读取数 | 两种来源，都只读：**一条日历地址**（Google 秘密地址、iCloud 公开共享、Outlook 发布链接、Nextcloud 公开分享），或**一套 CalDAV 凭据**（钉钉、企业微信、飞书、iCloud 私有、Fastmail、Nextcloud）。支持多条、可分别启用 |
| 只读的边界 | 只发读请求（`GET` / `PROPFIND` / `REPORT`），不写回、不创建、不删除、不读参会人、不碰会议链接 |
| 与系统日历的关系 | 系统日历告诉我"有个会"；Barge In 负责"现在，停下你手上的事" |
| 豁免工作时段 | 19:00 的会、周六的日程照常提醒；免打扰仍然生效 |
| 队列按事件 | 两个会挨着也能各提醒一次，逐条呈现，"还有 N 个" |
| 失败不丢提醒 | 拉取失败按上次缓存继续提醒，界面标注"数据可能过期"；认证失败单独提示 |
| 完成动作 | 「知道了」：不写回、不改事件，只记录 |
| 出厂默认 | 日程**停用**；添加订阅并成功拉取后提示开启 |

### v0.4（闹钟）

| 功能 | 说明 |
|---|---|
| 第四个场景 | 闹钟：你自己定下的时刻。每条一个时刻加一句内容，到点用同一套呈现把你拽出来 |
| 两种重复 | **每天**（每个非休息日）或**仅一次**（未来 7 天内的一天）。不提供"选星期几"：星期只有一个来源，就是通用的休息日 |
| 受通用时间约束 | 时刻不在工作时段内、或一次性那天是休息日，这一条标成「不会响」并写明原因；不参与调度、不计入今天、不记账本。改一次通用时间就立即重判 |
| 无效是派生的 | 不落盘、不算错误状态；修好工作时段或改回工作日，它就自己恢复 |
| 一次性会消散 | 响过、被关闭，或过了那一天，就从列表消失；每天闹钟长期留在列表里 |
| 补发窗口 | 一次性闹钟有 60 分钟补发窗口，并被当天工作时段结束封顶；重复闹钟错过就等下一次 |
| 账本照旧 | 跳过与完成都只记录，不改变呈现；账本按场景各一份 |
| 出厂停用 | 没有闹钟就没有数据；加第一条之后提示开启场景 |

### v0.4.3（更新检查）

| 功能 | 说明 |
|---|---|
| 自动检查更新 | 启动时与每 24 小时问一次 GitHub Releases 的最新正式版；只取版本号与发布说明，不发送任何数据。出厂开启，可在「通用」关掉 |
| 更新通知 | 用「温柔」那张卡呈现：右上角、一声提示音、不抢焦点。卡上只说这是 Barge In 的更新与版本号；点卡片打开设置·通用 |
| 每版一次 | 同一个新版本只通知一次；收起或点过之后不再出现。正在弹提醒或设置窗口开着时不叠卡 |
| 版本卡 | 「通用」里一张版本卡承载检查 / 可更新 / 下载 / 安装 / 失败；有新版时写出这次更新了什么（发布说明的第一个小标题），并给完整发布说明入口 |
| 一键更新 | 点「更新」下载安装包、校验版本与签名、替换当前 App 后自动重启；没有写入权限或不是打包后的 App 时，退回 Releases 手动下载 |

### v0.5（免费内容）

预设成为可扩展的资源：内置免费预设与预设格式。不做付费下载、不做市场、不做安装与卸载；定价与收费方式等真实用户再定。

### v1.0（正式发布）

公证签名、官网、下载页、文档完善。源码、文档与下载都在同一个公开仓库（MIT，见 [ADR-0005](adr/0005-open-source.md)）。

### 明确不做

统计图表、连续达标天数、成就系统、云同步、账号、iOS 端、摄像头确认、Apple Watch、AppleScript/Shortcuts 钩子、全局快捷键自定义、会议/录屏自动避让、代码级插件系统；预设的安装与卸载、manifest、目录扫描、素材运行时、字号配置。

**日程相关的明确不做**：新建/编辑/删除事件、写回日历、读取 `VALARM`、全天事件提醒、结束提醒、参会人与会议链接、日历颜色与分组、CalDAV 的写操作与增量同步、OAuth、内置 Google/iCloud/飞书登录。

**闹钟相关的明确不做**：选星期几（星期只有通用休息日一个来源）、节假日日历、自定义铃声与贪睡间隔、闹钟分组与历史、系统闹钟导入、iCloud 同步、任何待办语义（勾选完成、截止日、优先级、清单排序）。

**延后、等用户需求**：Google 私有日期的 OAuth 取数、Microsoft Graph 取数、企业 IM 的开放平台 API 取数、合并呈现（含闹钟与日程挨着到点）、优先级策略、久坐/空闲检测、活动的每日目标、付费预设与定价。

## 8. 已锁定的关键产品决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 平台 | 仅 macOS，原生 Swift | 用户是 Mac 个人用户；跨平台抽象是双倍成本换零收益 |
| 形态 | 菜单栏 + 提醒层 + 独立设置窗口 | 90% 的交互发生在被提醒的 10 秒，其余时间应当不存在 |
| 喝水模型 | 配额（日目标 + 进度） | 累计量与"连续坐姿时长"是两种不同模型，不强行统一 |
| 活动模型 | 纯定时，无配额、无久坐检测 | "到点起身舒展"是用户能理解的动作 |
| 日程模型 | 事件前置提醒，不是日历客户端 | 产品只负责打断，不负责排期；写回会让它变成半个日历 |
| 日程取数 | **两条只读传输：日历地址（ICS）与 CalDAV 账户** | 钉钉、企业微信、飞书、iCloud 私有都只给 CalDAV 凭据，一条 GET 拿不到；两种传输在解析层同构，多写一层不多写一套模型 |
| 日程的默认 | 前置 5 分钟；**出厂停用**；默认大字墙 · 标准 | 没有订阅就没有数据；提醒发生在会前，你还在独自工作 |
| 日程 vs 工作时段 | 日程**豁免**工作时段与休息日 | 19:00 的会与周六的日程不该被静默吞掉；事件自带时间 |
| 队列去重键 | `(场景, 事件标识)` | 喝水与活动行为不变；日程按事件各一条，不丢提醒 |
| 日程的"完成" | 「知道了」，不写回日历 | Barge In 不知道你有没有真去开会，也不该假装知道 |
| 闹钟模型 | 一条 = 一个时刻 + 一句话 | 它不是待办、不是日历事件：只说"现在，停下"，不带勾选与截止日 |
| 闹钟的重复 | 只有每天（每个非休息日）与仅一次（未来 7 天内） | 星期只有一个来源（通用休息日）；更远的事该进日历，由日程照样打断你 |
| 闹钟 vs 通用时间 | 受工作时段与休息日约束，冲突标成无效 | 你自己挑的时刻落在你工作的时候；冲突要看得见，不能静默吞掉 |
| 闹钟的补发 | 一次性 60 分钟、被下班封顶；重复错过不补 | 一次性不可恢复、重复可恢复；下班之后不该再弹一条工作提醒 |
| 闹钟的寿命 | 一次性关闭或过期即消失；每天长期保留 | 留在列表里的一次性闹钟等于待办清单的第一步 |
| 闹钟与日程 | 拆成两个场景，不合成一个 | 通用时间待遇相反、取数边界相反，见 [ADR-0002](adr/0002-alarms-vs-calendar.md) |
| 升级（强度加码） | **不做自动升级**：强度属于预设实例，账本只记录 | 这里的「升级」指强度随跳过次数加码，与 App 自身的更新是两件事；强度是用户选的，产品不根据记录偷偷加码（见 [ADR-0003](adr/0003-no-automatic-escalation.md)） |
| 频率 | 不设产品级上限 | 节奏由用户设；日程密度就是真实日程；防吵靠默认值、免打扰与场景开关 |
| 联网 | 只破"零网络"这一条，只读；日程订阅可选、默认关，更新检查默认开、可关 | 见 [ADR-0001](adr/0001-network-for-calendar-subscriptions.md) 与 [ADR-0006](adr/0006-update-check-network.md) |
| 更新 | App 内的更新检查与一键安装；通知固定用温柔卡；同一个版本只提醒一次 | 更新内容属于发布说明，通知卡只说"这是 Barge In 的更新"；摘要在设置里，避免把卡片做成更新日志（见 [ADR-0006](adr/0006-update-check-network.md)） |
| 凭据 | URL 里的 token 随地址存；用户名密码进 Keychain | 地址本身即凭据；密码不能进 `UserDefaults` |
| 失败策略 | 保留缓存继续提醒 + 明确标注过期 | "不静默丢弃"优先于"数据绝对新鲜" |
| 同时到点 | 提醒队列，逐条呈现，不静默丢弃 | 后续场景可能有强感知要求 |
| 合并呈现 | 本期不做，等用户需求 | 需要重新定义"主场景 + 附加行"的呈现与记录 |
| 节奏 | 固定间隔或指定时刻，不做动态追赶 | 用户痛点是"停不下来"，不是"节奏不对" |
| 呈现 | 三套预设（温柔 / 大字墙 / 碎裂），大字墙带强度，出厂默认大字墙 · 标准 | 三套资源覆盖"卡片"、"打断"与"砸醒"三种需求 |
| 预设资源 | 与场景解耦，四个场景共用 | 场景只提供默认文案与变量 |
| 强度 | 预设只能选档位，不能改数值 | 拦截输入=恶意软件语义；难度与压强由预设给出，不给用户一堆滑块去稀释它（见 §6 原则 1） |
| 中断 | 永远即时生效 | "可立即中断"是硬需求；队列也不取消后续 |
| 分发 | SwiftPM 构建；源码、文档与 App 在同一个公开仓库，MIT | 用户能看源码验证行为；维护两套仓库只会让文档与代码各说各话（见 [ADR-0005](adr/0005-open-source.md)） |
| 收费 | 全部功能免费；暂不做付费内容，定价等真实用户 | 收入是副产品；没有真实用户前不做商业设计 |
| 商业定位 | 个人副业，收入是副产品 | 品类天花板在副业量级 |

## 9. 提醒体验体系

**档位的来源**：不是四套预设，而是三套预设 + 大字墙的强度；碎裂的行为与"大字墙 · 标准"同档。四个档位是：温柔 / 大字墙 · 标准 / 大字墙 · 强硬 / 碎裂。它们是并列的呈现选择，不是升级阶梯。

**预设行为表**（预设只能选强度，不能自定义数值）

| 档位 | 呈现 | 推迟 | 中断按钮 | 中断方式 |
|---|---|---|---|---|
| 温柔 | 右上角卡片 + 单次提示音 | 允许 | 立即可点 | 双击 Esc 或单击 × |
| 大字墙 · 标准 | 满屏重复大字 + 渐强音 | 允许 | 立即可点 | 双击 Esc 或单击 × |
| 大字墙 · 强硬 | 满屏重复大字 + 渐强音 | 禁止 | 延迟 5 秒 | 双击 Esc 或单击 × |
| 碎裂 | 满屏碎玻璃 + 玻璃碎音 | 允许 | 立即可点 | 双击 Esc 或单击 × |

**Esc 一律双击**：任何档位都要在 1 秒内连按两次才中断，单击不生效；延迟还没走完时双击照样立即中断。× 按钮在延迟走完后单击即可。

**账本只记录**：跳过与完成都计入该场景的账本，但不改变下一次提醒；界面不展示跳过次数，也不做历史与统计。

**队列**：多个场景同时到点时，先到先呈现；当前关闭后立即呈现下一条，并显示"还有 N 个提醒"。每条用自己的预设与文案；完成 / 推迟 / 中断只记当前场景，不取消后面的。

**日程的呈现**：`大字词` 就是事件标题（"Q4 产品评审"铺满屏），进度行是"{start} 开始 · 还有 {minutes} 分钟"。它不需要像喝水那样给出"该做什么"——日历已经说了。

**闹钟的呈现**：`大字词` 就是这条的内容（"点外卖"铺满屏），进度行是到点时刻（"11:30"）。推迟过也用原定时刻，不让文案跟着推迟一起漂。

**视觉冲突**：大字墙是满屏重复的大字墙——大小字混排、7° 倾斜、每词各自旋转偏移、5 组错峰闪到全亮。冲突来自密度、凌乱与闪烁。强度不设上限（§6 原则 1）：呈现可以是遮挡、悬置、触觉与声音、时间渐变（1px 边 30 秒涨成满屏），或者一段叙事（满屏碎裂、涨上来的水）。设计新档位时只问"够不够狠、怎么实现"；涉及读取屏幕内容、跟随全局光标或阻止切 App 的做法会破原则 3、4，不能做。

**为什么不做自动升级**：强度属于预设实例，和文案覆盖同级——用户选了什么预设，就得到什么强度；产品不根据跳过次数偷偷加码。代价是"心流用户会一直点推迟"，我们接受它：把选择交给用户（强硬不可推迟），而不是交给一个用户看不见的升级算法。

## 10. 交互概要

- **首次启动**：设置窗口 + 温柔 / 大字墙 / 碎裂三张卡（默认大字墙 · 标准），这次选择同时落到四个场景；点"就用这个"后**立即按喝水场景真实呈现一次预览**（带一行"这是预览"标识；任何动作只关闭，不写状态不记账），随后窗口关闭、只剩菜单栏
- **日常**：只在菜单栏；点开看喝水进度、活动次数、下一场日程与下一条闹钟，点水位环记一杯、按住环 2 秒清空今日进度，免打扰 1 小时，或点"活动了"，进设置
- **被提醒**：满屏重复大字或右上卡片，一个动作结束；快速双击 Esc 随时中断；"完成"不受关闭延迟影响，也可在 1 秒内连按两次 Enter
- **同时到点**：逐条呈现，每一条底部显示"还有 N 个提醒"；关掉一条立刻下一条
- **日程**：在设置「日程」tab 里贴订阅地址 → 立即同步一次 → 看到"已同步 N 个事件" → 打开场景开关。地址失效或密码错，行内直接说原因，不去猜"网络错误"
- **闹钟**：在设置「闹钟」tab 点「添加闹钟」→ 改内容与时刻 → 选每天或仅一次 → 场景开关打开。条目与通用时间冲突时行内标成琥珀色的「不会响」并写明原因
- **设置**：单窗口，顶部「喝水 | 活动 | 日程 | 闹钟 | 通用」——场景页是当前场景的预设卡片 + 场景参数（喝水有配额、活动有节奏、日程有订阅与前置、闹钟有列表），通用页是四个场景共用的时间与开机自启
- **更新**：有新版时右上角出现一张温柔卡（"Barge In 有新版本 x.y.z"），点它打开设置·通用；在版本卡里看这次更新了什么、点「更新」下载并安装，App 自动重启；「发布说明」打开 GitHub 上的完整说明。关掉「自动检查更新」就不再自动联网，手动检查仍然可用
- **停用**：每个场景页顶部有"启用这个场景"开关；停用只停调度，不清账本与进度

详细规格见 [技术方案 §5](design.md)。

## 11. 发布与商业模式

**发布**

- 源码、文档与 App 下载都在公开仓库 `qiqiangvae/BargeIn`，MIT 许可（见 [ADR-0005](adr/0005-open-source.md)）
- 版本是带注释的 tag + GitHub Releases，附件是 `make app` 产出的 `.app` 压缩包
- 没有账号、没有云同步、没有遥测；更新检查只问 GitHub 一个版本号，关掉开关就不再问

**收入**

- 当前不收费；全部功能免费
- 不做订阅、不做账号、不做内购、不做市场
- 付费预设与定价：等真实用户再定；当前预设随包内置，不做下载与安装

**为什么这样选**

1. 用户能验证：源码公开，是"零权限、零网络、不做自动升级"这些承诺最硬的证据
2. 产品没有靠保密成立的护城河：复杂度在呈现与调度，抄走实现不会让任何人少走这段路
3. 只维护一套仓库，文档、代码与官网不会再各说各话

**必须承认的代价**：实现会被直接拿走；社区会提出与产品边界冲突的需求（待办、统计、云同步）。边界以本文档「明确不做」为准，不拿来换热度。

## 12. 度量

**不做遥测**。因此可观测的只有：

| 指标 | 含义 |
|---|---|
| Release 下载量 | 有没有人真的想试 |
| 公开仓库 star / issue 质量 | 问题是不是"有价值的问题" |
| 自己每天还在用吗 | 产品的第一号测试 |

**成功的定义（v0.4）**：自己连续用满两周，四个场景都没有被关掉，日程订阅一直在刷，闹钟列表里始终有三条以上；公开仓库发布后，有陌生人在 issue 里提具体的功能请求。

## 13. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **默认值风险** | 这个品类的用户第一周就会关掉提醒。默认温和 = 产品回到起点 | 出厂默认"大字墙 · 标准"；活动三个固定时刻；日程与闹钟出厂停用 |
| **推迟成为逃生口** | 没有自动升级后，默认标准允许推迟，心流用户可能一直点 | 要更狠选强硬（不可推迟）；产品不反制，接受这个取舍 |
| **场景太吵** | 四个场景叠加，一天可能 20+ 次 | 不设产品级上限；靠默认值错开、免打扰、场景开关；接受用户自己关掉 |
| **闹钟把产品拖成待办** | 一旦能自己写一句话提醒，用户会开始往里塞"下个月交材料" | 一次性只收未来 7 天；没有勾选、截止日、优先级与历史；过期即消失；文档与设置页明写边界 |
| **日程覆盖缺口** | CalDAV 覆盖了钉钉/企业微信/飞书/iCloud 私有，但 Google 私有与 Outlook 私有仍需 OAuth 或 Graph | 文档与设置页明写支持范围；不假装能通吃，把这两家放进延后项 |
| **联网叙事受损** | "零网络"曾是一句干净的卖点，现在要多解释两句（日程订阅、更新检查） | 都只读、都不上传内容；日程默认关、凭据进 Keychain；更新检查默认开但可关，关掉即不再联网；README 与设置页明写，不藏 |
| **更新装不上** | 没有写入「应用程序」的权限、不是打包后的 App、下载包被篡改，都可能失败 | 失败在版本卡里写明原因并给 Releases 手动下载；校验 bundle id、版本与签名后才替换；替换失败自动还原旧版本 |
| **凭据失效** | 秘密地址被重置、钉钉里重新生成了 CalDAV 密码，用户看到"没日程了"却不明白 | 认证/格式错误与"今天真没日程"分开说；连续失败退避并在界面上留痕 |
| **两套日历** | 系统日历的提醒同时响，变成双重打扰 | 文档说明定位差异：关掉系统日历的事件通知，或让 Barge In 只订阅工作时间那本日历 |
| 合并需求 | 有人嫌几条连着弹 | 本期不做；先观察 |
| **被直接复制** | 实现与素材可以被整体拿走 | 接受：护城河是迭代速度与克制；不为防抄增加任何复杂度 |
| **社区需求压边界** | 有人要求待办、统计、云同步 | 边界写死在「明确不做」；不合并不等于不礼貌 |
| 单人时间不足 | 副业，时间碎片化 | 里程碑按"可中断的周末块"切分 |
| 平台兼容 | 构建依赖 CLT，无完整 Xcode | 只用系统稳定 API；不引入第三方依赖 |
| 签名与公证 | 无 Developer ID 证书 | 面向开发者测试；公开仓库正式发布前再买证书做公证 |

## 14. 竞争与可行性结论

**竞争力**：真正的差异化不在"更硬"，而在**提醒呈现层被当作产品来做**——竞品把硬阻断藏在 JSON 开关里，把提醒样式写死在代码里。Barge In 把呈现做成第一等公民，再叠加四个场景、"用你自己的日历决定何时打断你"与"你自己定下的时刻也算数"这两个反过来的用法。它不做"越跳越硬"的自动升级：强度是用户选的预设属性。

**可行性**：技术上全部使用系统自带能力，无后端、无账号、无遥测；唯一的复杂度集中在日程的 ICS 解析与订阅失败处理，已被压到"一条 GET + 可选 Basic Auth"。商业上量级有限但真实，因此立项定位为副业。

**一句话结论**：这是一个**天花板不高但确定存在、投入可控、且有一个别人没占的位置**的产品。
