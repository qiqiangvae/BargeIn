# 更新检查联网：只问版本号，默认开、可关

产品直到 0.4.1 只有一个联网能力：日程订阅（[ADR-0001](0001-network-for-calendar-subscriptions.md)）。0.4.3 引入第二个：**App 自动检查更新**。结论：更新检查只向 GitHub Releases 读一次最新版本号与发布说明，不发送任何本机数据；出厂开启，可在「通用」关掉；关掉后不再自动联网，手动检查仍然可用。

**为什么**

- 分发只有 GitHub Releases，没有 App Store 的自动更新。没有检查更新，用户只能靠自己想起来去下载——一个已经装着旧版的工具，最容易被忘掉。
- 提醒要复用产品自己的呈现：发现新版本时不该弹一个系统通知（那会要求通知权限，也与「提醒的呈现就是产品」冲突），而应该用用户认得的那张温柔卡。
- 检查必须是只读的：`GET` 一个公开 feed，不附带用户标识、不统计、不区分人群。与日程订阅一样，它是"请求别人的公开数据"，不是"上报自己"。

**怎么做**

- 版本号与发布说明都从 `https://github.com/qiqiangvae/BargeIn/releases.atom` 取（GitHub 的公开 releases feed）。第一版用 `HEAD` 请求 `releases/latest` 的重定向取版本号，但发布说明还要再取一次；atom 一次就够。
- **不走 GitHub API**：未登录的 API 每小时只有 60 次，共享出口 IP 很容易被限流（实测 403），而 atom feed 没有这个限制。
- 安装包地址按发布命名约定拼：`https://github.com/qiqiangvae/BargeIn/releases/download/<tag>/Barge-In-<版本>-macos-arm64.zip`。
- 「这次更新了什么」取发布说明 HTML 的第一个 `h1`–`h3` 小标题；没有标题就用发布名。发布流程据此约定：**正文第一段用 `## …` 写这次改了什么**，标题不要只写版本号。
- 通知固定用温柔卡，卡上只说「Barge In 有新版本 x.y.z」与当前版本；摘要放在设置·通用的版本卡里，卡上不堆正文。
- 安装：下载 → 解包 → 校验 bundle id、版本与 `codesign` 签名 → 由一段脚本在本进程退出后替换当前 `.app` 并重新打开；失败自动还原旧版本。

**边界**

- 检查频率是启动时一次 + 每 24 小时一次；关掉开关立刻停止计时器，正在进行的下载不受影响。
- 每个新版本只通知一次；正在显示提醒或设置窗口开着时不叠卡。
- 只接受 `.app` 内运行；没有写入当前目录的权限、校验不过、解包失败都只影响这一次更新，不阻塞 App 本身。
- 不做：增量更新、回滚入口、渠道/灰度、系统通知中心、后台静默替换（替换时 App 会退出并重开）。

**代价**

- 破了"日程订阅是唯一联网功能"的叙事，必须靠"只读、默认可关、可自证"解释；README、设置页与官网同步写明。
- 未公证的 ad-hoc 签名意味着更新包无法做 Developer ID 校验，只能用 bundle id + 版本 + 自身签名校验；真正的信任仍依赖 HTTPS 与源码公开。
- 发布说明的摘要依赖发布流程的书写约定；写成标题就能用，不写就退回发布名。

**被否掉的方案**

- 走 GitHub API：给发布说明与安装包元数据更直接，但未登录配额会被共享 IP 打满（实测 403），用户看到的只会是"检查失败"。
- 打开 Releases 页面让用户手动下载：不用安装逻辑，但"点了更新就能用"是这次需求本身。
- 系统通知中心：要多一个权限，且与既有提醒呈现割裂。
